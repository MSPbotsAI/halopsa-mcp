## 需求理解

一句话：alopsa_tickets_update 工具中缺少ticket_type 字段，需要增加

复述：`halopsa_tickets_update` 这个 MCP 工具目前没有暴露"修改工单类型"的入参，导致依赖它的工作流（原文：Original Report 提到"需要增加"）在改单时改不了工单类型，卡住或被迫绕过。成功的样子是：调用方在调 `halopsa_tickets_update` 时可以像 `halopsa_tickets_create` 一样传一个工单类型 id，改单会把 HaloPSA 上那张工单的类型也一并改掉；不传就维持原样，不影响任何现有调用方。工单本身只有 Original Report 一处诉求，描述结构化字段（Steps to Reproduce / Expected / Actual）和 Original Report 三处表述一致，没有互相矛盾，没有 comment 需要额外核对（本单历史上两条 comment 都是本流水线自己发的 BLOCKED，见「工单往来」）。

## 现状

- `src/domains/tickets.ts:239-275` —— `halopsa_tickets_create` 的 `inputSchema` 含 `tickettype_id: { type: "number" }`，且 `required` 数组包含它（:273），建单必须指定类型。
- `src/domains/tickets.ts:277-341` —— `halopsa_tickets_update` 的 `inputSchema.properties` 里没有 `tickettype_id`、也没有 `ticket_type` 或任何同义字段；`required` 只有 `ticket_id`（:339）。这就是工单描述的缺陷本身：改单这条路径上完全没有暴露类型字段，不是校验拒绝、是入参里根本不存在。
- `src/domains/tickets.ts:477-508` —— create 的 handler 把 `args.tickettype_id` 原样放进 `payload.tickettype_id`（:488），再传给 `client.tickets.create(payload)`（:496）。
- `src/domains/tickets.ts:510-541` —— update 的 handler 组装的 `payload` 里没有任何类型相关字段（:517-526），传给 `client.tickets.update(ticketId, payload)`（:529）。
- `src/domains/tickets.ts:82-95`（`parseCustomFields` 上方的注释）明确写着"`client.tickets.update` spreads its data argument into the Halo payload verbatim"——SDK 在这一层不做字段白名单或改写，`payload` 里放什么就原样发给 HaloPSA，这条机制对 create/update 一致。
- `src/domains/lookups.ts:7`（模块头注释）写着"`halopsa_tickets_create` requires a `tickettype_id` and `halopsa_tickets_update` takes `status_id` and `priority_id`"——这是对现状的如实描述，不是"刻意不做"的设计记录；本仓库没有任何 commit message、ADR 或 issue 讨论过"update 不该支持改类型"，是历史遗留的省略，不是策略。
- `src/utils/ticket-shape.ts` + `src/__tests__/ticket-shape.test.ts:16-18` —— 证实 `tickettype_id`/`tickettype` 是工单实体本身携带的可读标量字段（`compactTicket` 把它当展开引用折叠成 `{id, name}`），不是只在创建那一刻才存在的一次性输入，说明类型本来就是工单的可变属性。
- `src/domains/lookups.ts:171-178, 262-266` —— `halopsa_lookups` 工具（kind: `ticket_types`）可以把租户当前配置的工单类型列成 `{id, name}`，且已建议"pass tickettype_id"给状态/分类查询用；调用方今天已经能读到合法的类型 id 列表，缺的只是把它写回 update。
- wiki：`ProductDocs/_field-index.md § Field Index — Platform (agent.mspbots.ai)` 记录了 HaloPSA connector 在 Agent Platform 上的连接配置字段（Tenant / Base URL / Client ID / Client Secret，_verified_ 2026-08-31）与"每个连接器有一份对用户可见的 Tools 清单（工具名 + 一行描述 + Available 徽标）"这条产品事实（`ProductDocs/15-Capabilities.md § Connector detail view`，_verified_ 2026-08-27/2026-08-31）——说明本次改动对最终用户的可见面是：SOP agent 在用这个连接器时，`halopsa_tickets_update` 能接受的参数集变了，但连接器本身怎么连、怎么鉴权不受影响。**wiki 未覆盖 `ticket_type`/`tickettype_id` 这个工具入参字段本身**——ProductDocs 记录的是 Agent Platform 界面上人工可配置的项，不下钻到每个连接器 MCP 工具的 inputSchema 明细，这条属于预期之外的覆盖范围，不是巡检遗漏。

## 产品设计

### 目标 / 非目标

- 目标：`halopsa_tickets_update` 增加一个可选入参，允许调用方（SOP agent / 直接调 MCP 工具的客户端）在更新工单时一并修改工单类型；不传时行为与今天完全一致。
- 非目标：
  - 不改 `halopsa_tickets_create` 的行为（它已经支持类型）。
  - 不新增校验 UI、不新增 Agent Platform 页面元素——这是 MCP 工具层的入参变化，不涉及 `agent.mspbots.ai` 任何界面（见「现状」wiki 引用，连接器的连接配置与本次改动无关）。
  - 不处理"工单类型变更后，原类型专属的自定义字段/分类是否要联动清空"这类 HaloPSA 侧的业务规则——那是 HaloPSA 服务端自己的行为，本工具只负责把值传过去，不代为决策。

### 方案（用户可见行为）

#### 主流程

1. 调用方（SOP agent 或直接调用方）已经拿到目标工单的合法类型 id（通常先调 `halopsa_lookups`，`kind: "ticket_types"` 读到租户当前配置的类型列表）。
2. 调用 `halopsa_tickets_update`，除已有参数外，附带新参数（命名与含义见「Open Questions」）指定新的类型 id。
3. 调用成功后，返回的工单数据里类型字段（`tickettype` / `tickettype_id`，即 `halopsa_tickets_get` 已经会返回的同一批字段）反映为新值。
4. 调用方不传这个参数时，行为和今天完全一样——工单类型不受影响。

#### 界面与交互变化

无——这是一个 MCP 工具的输入参数变化，面向的是调用 MCP 协议的 agent/客户端，不是人操作的图形界面。Agent Platform 上"连接器详情页 Tools 列表"会展示 `halopsa_tickets_update` 的名称与一行描述（现状已验证的产品事实），本次改动预期不改这行描述文案（工具描述当前是"Update ticket, including reassigning it to a different agent or team"，是否要在描述里也提一句"and ticket type"留给实现者按仓库既有文案风格判断，不影响验收）。

#### 边界与异常

- 不传新参数：不受影响（见主流程步骤 4）。
- 传入的类型 id 在该租户下不存在，或该类型已被禁用：HaloPSA 服务端应该拒绝这次修改并返回错误；调用方看到的是一次明确失败的调用，不是"看起来成功但类型没变"的静默失败。
- 传入的类型 id 是数字但不是整数、是负数、是 0：交给 HaloPSA 服务端校验（工具层只做类型层面的 `number` 校验，不在本工具里重复业务规则）。
- 同一次调用里既改类型又改分类（`category_1..4`）：HaloPSA 侧的既有事实是"某些状态/分类只对特定工单类型开放"（`lookups.ts:265` 已有的产品说明），两者会不会互相冲突、谁生效谁不生效，取决于 HaloPSA 服务端顺序处理这次请求的方式，工具层原样透传，不做二次编排。

#### 权限与多租户

- 权限模型不变：`halopsa_tickets_update` 今天允许改哪些字段、被哪个凭据授权，由该次请求绑定的租户凭据（`getCredentials()`，见 `src/utils/client.ts`）决定，本次改动不引入新的鉴权分支，新参数和 `status_id`/`priority_id` 等既有参数走同一条鉴权路径。
- 跨租户不可见性：每次调用的凭据在网关模式下通过 `AsyncLocalStorage` 按请求隔离（`src/utils/client.ts` 现状已读），本次改动没有新增任何跨请求共享的状态，不改变这条隔离机制，也不引入新的跨租户风险面。

### 影响面

- 受影响的调用方：所有会调用 `halopsa_tickets_update` 的 SOP agent / 直接客户端——影响是新增能力，不是行为变更，新增的入参是可选的，向后兼容，不影响任何现存调用。
- 老数据/老配置：无需迁移。这是工具入参 schema 的增量变化，不涉及本仓库自身的存储或配置。
- 是否需要公告：建议在下一次连接器版本发布说明（`CHANGELOG.md`，走 `semantic-release`）里提一句"`halopsa_tickets_update` 现在支持修改工单类型"，方便已有 SOP 依赖这个缺口写过 workaround 的用户知道可以切回直接调用；不强制。

### 验收标准 AC1..ACn

- AC1: Given 一个已连接 HaloPSA 的租户，调用方对一张已存在的工单调用 `halopsa_tickets_update` 并传入该租户下合法的工单类型 id，When 调用返回成功，Then 该工单在 HaloPSA 里的类型已变为新值，且本次调用的返回结果中类型字段（`tickettype`/`tickettype_id`）体现新值。
- AC2: Given 同上环境，调用方调用 `halopsa_tickets_update` 但不传类型相关参数，When 调用返回成功，Then 该工单的类型保持调用前的值不变（新参数不影响未使用它的调用）。
- AC3: Given 调用方传入的类型 id 在该租户下不存在/不合法，When 调用 `halopsa_tickets_update`，Then 调用返回明确的错误（`isError`/抛出异常，与本工具其它字段校验失败的既有表现一致），不返回"成功但类型未变"的结果。
- AC4: Given 一个 agent 读取 `halopsa_tickets_update` 工具的 `inputSchema`（例如通过 MCP 的工具发现/`tools/list`），When 读取，Then 新增的类型参数出现在 `properties` 里且不在 `required` 数组中——确认这是一个可选新增，不是破坏性变更。
- AC5（多租户）: Given 两个不同租户各自连接了各自的 HaloPSA 实例，When 租户 A 的凭据下调用 `halopsa_tickets_update` 修改工单类型，Then 该次调用只对租户 A 自己 HaloPSA 实例里的那张工单生效，不影响、也读不到租户 B 的任何工单或类型数据（验证本次改动没有破坏既有的按请求凭据隔离）。

### Open Questions

- [已假设] 新参数命名——工单原文写的是 `ticket_type`，但仓库里 `halopsa_tickets_create`、`halopsa_lookups` 现有的同义字段一律叫 `tickettype_id`（与 HaloPSA 原生字段名一致）。本设计假设新参数沿用 `tickettype_id`，理由是与仓库既有命名和 HaloPSA 自己的字段名保持一致，比照字面翻译工单措辞更不容易在实现里产生"这是不是另一个字段"的歧义。若评审认为应该贴合工单原话叫 `ticket_type`，第 4 节 schema 与技术设计第 4/5 节要相应改名，不影响其余设计。
- [不阻塞] 是否应该在改类型的同时允许联动清空/校正与旧类型绑定的分类字段——按现状调研，这是 HaloPSA 服务端自己的业务规则（`lookups.ts:265` 已经说明状态/分类可能被限定到特定工单类型），本工具只透传参数，不做二次编排，默认按"不额外处理，出错交给 HaloPSA 返回"处理；如果验收时发现某些租户配置下这会导致体验很差，再由需求方决定是否要工具层介入。
- [不阻塞] 工具描述文案（"Update ticket, including reassigning it to a different agent or team"）是否要顺带更新为提及类型——默认不改，交给实现者视改动大小决定，不影响验收标准。

## 技术设计

### 结论

在 `src/domains/tickets.ts` 的 `halopsa_tickets_update` 工具定义里新增一个可选入参 `tickettype_id: { type: "number" }`（与 `halopsa_tickets_create` 同名同类型），并在对应 handler 组装 `payload` 时把 `args.tickettype_id` 原样透传给 `client.tickets.update()`——和 `priority_id`/`status_id` 现有字段的处理方式完全一致。不改鉴权、不改 SDK 版本、不改客户端凭据逻辑，因为 `client.tickets.update` 已确认是"参数原样透传给 HaloPSA"（`tickets.ts:91` 注释），create/update 走的是同一个 Ticket 实体、同一条透传机制，`tickettype_id` 对 create 有效即有理由认为对 update 同样有效。改动局限在一个文件的 schema 声明 + handler 两处 + 对应测试文件新增用例。

### 现有实现定位

- `src/domains/tickets.ts:239-275` —— `halopsa_tickets_create` 的 `inputSchema`：`tickettype_id: { type: "number" }`（:253-255），`required` 含 `tickettype_id`（:273）。新参数照抄这个字段定义，去掉 required。
- `src/domains/tickets.ts:277-341` —— `halopsa_tickets_update` 的 `inputSchema`：本次要改的地方，`properties` 里插入 `tickettype_id`，`required` 不变（仍只有 `ticket_id`，:339）。
- `src/domains/tickets.ts:477-508` —— create 的 handler：`payload.tickettype_id: args.tickettype_id as number`（:488）是新字段透传写法的参照对象。
- `src/domains/tickets.ts:510-541` —— update 的 handler：本次要改的地方，`payload` 对象（:517-526）里插入 `tickettype_id: args.tickettype_id as number | undefined`，紧跟 `priority_id` 之后、`agent_id` 之前，与 schema 里的顺序保持一致。
- `src/domains/tickets.ts:82-95` —— `parseCustomFields` 上方注释，确认 `client.tickets.update` 对 `payload` 做的是逐字段透传（verbatim spread），不是白名单过滤，这是本次改动能生效的关键前提。
- `src/domains/lookups.ts:243-274` —— `halopsa_lookups` 工具，调用方用它读到租户当前合法的 `ticket_types`（`{id, name}`），本次改动不需要修改这个文件，只是它现有能力正好是新参数的输入来源。
- `src/__tests__/domains/tickets.test.ts:151-158`（create 的 required 断言）与 `:270-340`（update 现有测试组，尤其 `:284-297` "should pass update fields to API"）是新增测试要落笔的地方——照抄 `:284-297` 那条测试的形状，断言 `mockTicketsUpdate` 被调用时 payload 里带上了 `tickettype_id`。

### 方案选型

无备选：这是一个字段级别的 schema 增量 + 透传，仓库里 create 已经用完全相同的机制实现了同一个字段，没有第二种自然的做法（比如"做成 custom_fields 的一项"不成立——`tickettype_id` 是 Halo Ticket 实体的原生字段，不是租户自定义字段，混进 `custom_fields` 反而破坏了工具现有对"内建字段 vs 自定义字段"的区分）。

### 改动清单

- `src/domains/tickets.ts` [改] —— 两处：(1) `halopsa_tickets_update` 的 `inputSchema.properties` 新增 `tickettype_id` 字段定义（紧跟 `priority_id`，:295-297 之后），带一句 description 说明"可选，通过 `halopsa_lookups`（kind: `ticket_types`）解析名称到 id，省略则工单类型不变"；(2) 该工具的 handler 内 `payload` 对象新增一行 `tickettype_id: args.tickettype_id as number | undefined,`（紧跟 :521 的 `priority_id` 之后）。
- `src/__tests__/domains/tickets.test.ts` [改] —— 在现有 `describe("halopsa_tickets_update", ...)` 组（约 :270 起）新增至少两条用例：(1) 传 `tickettype_id` 时，`mockTicketsUpdate` 收到的 payload 含该字段；(2) 不传时，payload 里该字段是 `undefined`（沿用 :284-297 那条测试的断言写法：整个 payload 对象做精确匹配）。
- `CHANGELOG.md` [不改] —— 由 `semantic-release` 在合并到 `main` 后自动生成，本次改动不手写。

### 数据与接口契约

- MCP 工具：`halopsa_tickets_update`
  - 新增请求参数（可选）：
    ```json
    {
      "ticket_id": 50444,
      "tickettype_id": 3
    }
    ```
  - 响应契约不变——仍是现有 `shape()`/`compactTicket()` 处理后的工单 JSON，新值体现在已有的 `tickettype`/`tickettype_id` 字段上（`src/utils/ticket-shape.ts` 现有逻辑，见 `ticket-shape.test.ts:16-18`），不新增响应字段。
  - 错误契约：不新增错误类型，沿用现有 `catch (error) { logTicketError("update", error); throw error; }`（:537-539）——HaloPSA 服务端对非法 `tickettype_id` 的拒绝会以 SDK 抛出的异常形式冒泡上去，和其它字段校验失败一致。
- 下游 HaloPSA REST API：`client.tickets.update(ticketId, payload)` 内部对应 HaloPSA 的 `PUT /Tickets`（同一个 Ticket 资源，create 对应 `POST /Tickets`）。**未在本环境完成的验证**：`@wyre-ai/node-halopsa` SDK 托管在私有 npm registry（`npm.pkg.github.com`），本次设计所在环境没有 `NODE_AUTH_TOKEN`，无法 `npm ci`/查看 SDK 的 TypeScript 类型定义来逐字确认 `update()` 的 `data` 参数类型是否显式列出了 `tickettype_id`。技术设计的结论基于两条间接但扎实的证据：(a) `tickets.ts:91` 注释明确说 update 对 payload 是"verbatim spread"，SDK 不做字段白名单；(b) create/update 面向的是 HaloPSA 同一个 Ticket 资源，字段模型应该一致，且 `tickettype_id` 已确认是工单实体的常驻标量字段（不是仅创建时特有的输入）。**建议开发棒在有 registry 凭据的环境里用一条 `npm ci` 之后确认这条假设**，或者直接对着一个 HaloPSA 沙箱租户跑一次真实调用（S9 测试策略里也是这么安排的）。
- 无 DB 变更（本仓库不持有自己的数据库，是无状态的 MCP 网关）。

### 关键流程时序

```
Agent/客户端 -> MCP Server(halopsa_tickets_update, {ticket_id, tickettype_id,...})
MCP Server(tickets.ts handler) -> 组装 payload（含 tickettype_id）
MCP Server -> node-halopsa SDK: client.tickets.update(ticketId, payload)
node-halopsa SDK -> HaloPSA REST API: PUT /Tickets（payload 原样透传）
HaloPSA REST API -> 校验 tickettype_id 在该租户下是否合法
  合法: HaloPSA -> SDK -> MCP Server: 更新后的工单（含新 tickettype）
        MCP Server -> shape()/compactTicket() -> Agent/客户端: 折叠后的工单 JSON
  不合法: HaloPSA -> SDK 抛错 -> MCP Server 的 catch 分支 -> logTicketError -> 异常向上抛给调用方
```

### 非功能

- 幂等与并发：`halopsa_tickets_update` 本身是一次性的 PUT 语义，重复调用同一个 `tickettype_id` 是幂等的（把类型设成同一个值不会产生副作用）；本次改动不引入任何新的并发面，沿用工具现有的无状态请求处理。
- 性能：新增一个 number 字段的透传，不新增额外的网络往返或计算，性能影响可忽略。
- 安全：不新增鉴权分支，`tickettype_id` 和 `status_id`/`priority_id` 走同一条既有的凭据校验路径（`getCredentials()`）；日志方面，`logTicket("update args", args)`（:514）和 `logTicket("update payload", ...)`（:527）会把新字段一并记入 trace 日志，和现有字段一致，不是敏感数据（工单类型 id 不是凭据），无需脱敏。
- 多租户隔离：见产品设计「权限与多租户」——凭据按请求隔离（`AsyncLocalStorage`），本次改动不新增跨租户共享状态。
- 可观测：复用现有的 `logTicket`/`logTicketError` 机制，无需新增日志点；如果 AC3（非法类型 id 报错）在真实调用中定位困难，可以在 catch 分支里追加"是否是 tickettype 校验失败"的判断，但这超出本次最小改动范围，留给实现者按需要决定。

### 上线与回滚

- 本仓库无 feature flag 机制（`grep` 未见相关基础设施），新参数是可选字段，天然是"灰度安全"的——不传就没有任何行为差异，不需要额外的灰度开关。
- 发布顺序：单仓库改动，`main` 分支合并后由 `.releaserc.json` 配置的 `semantic-release` 自动生成新版本、更新 `CHANGELOG.md`、发 GitHub Release（`npmPublish: false`，不发 npm 包）。建议提交信息使用 `feat(tickets): add optional tickettype_id to halopsa_tickets_update`（Conventional Commits 的 `feat` 前缀，触发 minor 版本号），仓库 `CONTRIBUTING.md` 已经这么约定。
- 回滚：新参数是纯增量、非破坏性变更，出问题时回滚等价于 revert 这一个 commit 并重新发布，不涉及任何数据迁移或兼容性清理。

### 测试策略

- 单测（`vitest`，`npm run test`）：在 `src/__tests__/domains/tickets.test.ts` 现有 `halopsa_tickets_update` 测试组新增两条（见「改动清单」），mock `client.tickets.update` 断言 payload 携带/不携带 `tickettype_id`——这部分可以完全自动化，不依赖真实 HaloPSA 环境。
- 集成/手工验证：需要一个连接了真实（或沙箱）HaloPSA 租户的凭据，实际调用 `halopsa_tickets_update` 传 `tickettype_id`，用 `halopsa_tickets_get` 读回确认类型确实变了——这一条在本设计所在环境无法执行（没有 HaloPSA 测试租户凭据），是 AC1/AC3 里"HaloPSA 服务端真实行为"这部分的验证方式，留给开发棒在有凭据的环境里做，或标记为"环境依赖，需人工在有沙箱租户时补验证"。
- 回归面：本次改动只新增一个可选字段，不修改任何现有字段的处理逻辑，回归面很窄——重点回归 `halopsa_tickets_update` 现有测试全部仍然通过（尤其"不传新字段时 payload 不含该字段"这条隐含契约，见改动清单第二条）。

### 工作量与拆分

- 预估：0.5–1 人日（含读代码、改 schema+handler、补单测；不含 HaloPSA 沙箱环境搭建，如果需要新搭建沙箱环境验证 AC1/AC3 会显著增加，视是否已有现成测试租户而定）。
- 不建议拆分子任务——改动小到没有可以独立交付的中间状态，拆分反而增加协调成本。

### 风险与依赖

- 风险 1（中）：`client.tickets.update` 是否真的把 `tickettype_id` 透传给 HaloPSA 且 HaloPSA 接受——技术设计给出的是间接证据（见「数据与接口契约」），不是逐字确认过的 SDK 类型签名或 HaloPSA 官方文档。缓解：开发棒落地时优先用真实/沙箱租户跑一次，而不是只信任 mock 测试通过。
- 风险 2（低）：某些 HaloPSA 租户可能配置了"某些状态/分类只对特定工单类型开放"的规则（`lookups.ts:265` 已有产品说明），改类型和改分类/状态在同一次调用里的交互行为由 HaloPSA 服务端决定，工具层不感知也不编排——如果验收时发现这个组合调用体验差，需要回 groom 讨论是否要工具层介入（不在本次范围内）。
- 依赖：无跨工单依赖；依赖 `@wyre-ai/node-halopsa` SDK 当前版本（`^1.1.0`）已支持的透传机制，不需要升级 SDK 版本。
