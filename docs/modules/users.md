# Module: users (`src/domains/users.ts`)

Accumulated facts, appended after each ticket ships. Do not rewrite existing sections.

## PRD-20396 · 2026-10-13

- `halopsa_users_search` / `_get` / `_create` / `_update` were added (`src/domains/users.ts`; sha is this ticket's work-branch HEAD, see `docs/tickets/PRD-20396.md`'s Handoff section for the exact value — not yet merged to `main` as of this entry). The domain exposes HaloPSA contacts under the `halopsa_users_*` tool-name convention (matching every other domain's `halopsa_<domain>_<action>` pattern), but **the installed SDK's resource property is `client.contacts`, not `client.users`** (`src/utils/client.ts`'s `getClient()` returns a `HaloPsaClient` whose field is `readonly contacts: ContactsResource`, confirmed by reading `@wyre-ai/node-halopsa@1.1.0` source, tag `v1.1.0`, commit `b0622b1f7b789a28f543424b9c39fc8978254fda`, cloned from the public `github.com/WYRE-AI/node-halopsa` — see "Dependency workaround" below). The SDK's HTTP path is `/Users` and its list response key is `users`, so the tool-facing shape (`{record_count, users: [...]}`) matches what the ticket's design assumed; only the **client accessor name** differs (`.contacts`, not `.users`). Any future domain touching this entity should call `client.contacts.*`, not `client.users.*` (the latter does not exist and would throw `Cannot read properties of undefined`).
- The SDK's `Contact` type field for email is **`emailaddress`, not `email`** (`node-halopsa` `src/types/contacts.ts`). `users.ts` keeps the tool-facing property named `email` (for consistency with `clients.ts`'s `halopsa_clients_create`, which also uses `email`) and translates it to `emailaddress` only at the `client.contacts.create`/`.update` call boundary; the raw SDK response (which contains `emailaddress`) is passed straight through unmodified on reads.
- **`ContactCreateData` requires `client_id: number`** (a HaloPSA contact is always a child of a client/company) — this was unverified at design time (design doc's Tech design §11 flagged the SDK's actual shape as unread) and turned out to add one more required input field than the ticket's own wording ("name + email") anticipated. `halopsa_users_create`'s `inputSchema.required` is `["name", "email", "client_id"]`.
- **Duplicate-prevention on create** (AC6/AC7): implemented as `client.contacts.list({search: email})` then an exact, case-insensitive match of each row's `emailaddress` against the requested email, client-side — not relying on HaloPSA's own `search` matching semantics to be exact (a looser/fuzzy server-side match could both over- and under-report duplicates). This is a read-then-write with no transactional guarantee; accepted as-is per the ticket's own wording ("prevent duplicates" describes a check, not a lock), consistent with HaloPSA having no unique email constraint to fall back on either.
- **Partial-update mechanism** (AC7/AC8, `halopsa_users_update`): reuses `tickets.ts`'s existing "build a payload object with every optional field set to `args.<field> as T | undefined`" pattern verbatim. Confirmed (not just assumed) that this actually works for the Contacts endpoint by reading the SDK's own `src/http.ts:109` (`body: body ? JSON.stringify(body) : undefined`) — `JSON.stringify` drops object keys whose value is `undefined`, so a caller-omitted field never reaches HaloPSA, letting `inactive` double as activate/deactivate with no separate tool.

### A fifth enumeration site in `mcp-server.ts`, missed by this ticket's own design

The design doc (Tech design, Change list) counted four places that hand-enumerate the domain list: `utils/types.ts`'s `DomainName` union, `domains/index.ts`'s switch + `getAvailableDomains()` array, and three spots inside `mcp-server.ts` (the local `Domain` type, `domainDescriptions`, and the `halopsa_navigate` tool's inline description string). **There is a fifth, and it is the one that actually matters for the tools to work**: `createMcpServer()`'s `CallToolRequestSchema` handler routes every incoming `tools/call` through a chain of `if (name.startsWith("halopsa_<domain>_"))` checks before falling through to an "Unknown tool" response. Forgetting to add `halopsa_users_` / `halopsa_sites_` branches here means the new tools appear correctly in `tools/list` (so `getAvailableDomains()`/the navigate tool look fine) but every actual call to them returns `Unknown tool: halopsa_users_search. Use halopsa_navigate to discover available tools by domain.` — a failure mode that unit tests calling the domain handler directly (`usersHandler.handleCall(...)`) do **not** catch, because they bypass `mcp-server.ts` entirely. Caught here only by an end-to-end stdio smoke test (`node dist/index.js` + a raw `tools/call` JSON-RPC request) during self-test, not by the unit suite. **Any future domain addition must grep `mcp-server.ts` for `name.startsWith("halopsa_` to find all five sites, not just the four the Change-list template enumerates.**

### Dependency workaround (cross-reference, not new)

`@wyre-ai/node-halopsa` is on GitHub Packages (`npm.pkg.github.com`), which 401s without a `NODE_AUTH_TOKEN` even for installs of this public-source package — see `docs/modules/tickets.md`'s PRD-19482 entry for the full workaround (clone the public source repo at the matching version tag, `npm install && npm run build` locally, temporarily point `package.json`'s dependency at `file:<local path>` to seed `node_modules`, then restore `package.json`/`package-lock.json` to the registry version — `node_modules` is unaffected by the revert). Re-confirmed working on this ticket, 2026-10-13, tag `v1.1.0`.

### Test coverage note

`src/__tests__/domains/users.test.ts`'s "multi-tenant isolation" test (AC10/TC-HALO-014) substitutes a direct `AsyncLocalStorage` harness for the literal `runWithCredentials()` + `credentialKey()`-cache path, to stay deterministic without invoking the real SDK/network from inside a `vi.mock`-ed test file (a `vi.doUnmock` + `vi.resetModules()` attempt to exercise the *real* `utils/client.ts` + real SDK constructor was tried and abandoned — the externalized `file:`-linked SDK package did not reliably pick up `vi.doMock` after a mid-test module reset, and chasing that further was not a good use of this ticket's time). The generic cache/isolation mechanism itself is unmodified by this ticket and is already covered by this repo's own `src/__tests__/client.test.ts`.

## PRD-20396 · 2026-10-14 (rework, INT findings F1 + F3)

- **`halopsa_users_create`'s duplicate-check search now passes `inactive: true`** (`src/domains/users.ts:157` area, this round's commit, work-branch sha: see `docs/tickets/PRD-20396.md`'s "Rework round" handoff entry). Without it, HaloPSA's `/Users` list excludes inactive contacts by default (`ContactListParams.inactive`, `@wyre-ai/node-halopsa@1.1.0` `src/types/contacts.ts:34-35`, confirmed against the same local SDK clone as the "Dependency workaround" entry above, tag `v1.1.0`), so a duplicate-check against a deactivated contact's email silently returned 0 rows and let a second contact be created — found on INT (tenant `mspbotstest`, contacts 125/126) by Minnie Zhou, `[TEST · PRD-20396]`, 2026-10-14. **Any future duplicate/uniqueness check against this SDK's list endpoints must consider whether `inactive`-type rows need to be included** — this repo's `clients.ts`/`sites.ts` do not currently have an analogous duplicate-check, so this is the first precedent.
- **When a match is inactive, `existing_contact` now includes `inactive: true`** and `reason` points the caller at `halopsa_users_update` to reactivate instead of creating a new record. This is a deliberate AC6 amendment (an inactive-email match now counts as a duplicate, not just an active one) — approved by Tom the same round it was reported, not independently re-confirmed by design/groom (see `docs/tickets/PRD-20396.md`'s AC6 note).
- **`halopsa_users_create`'s `site_id` now defaults to the client's `main_site_id`** when omitted (`client.clients.get(client_id).main_site_id`, reusing the `clients.ts` resource already used elsewhere in this repo — no new SDK surface). Root cause: HaloPSA's `/Users` endpoint requires a site and returns 400 `"A Site must be selected"` when none is given — found on INT on the same round. If a client has no `main_site_id` configured, this falls through to `undefined` and HaloPSA will still reject the create; this residual edge case is not handled further (out of scope for this round — the ticket's original wording ("site_id, if known") did not anticipate HaloPSA requiring it at all, so a client with literally no main site is an even narrower edge not reported by INT testing).
- **Environment note (re-confirmed, not new)**: the GitHub Packages 401 workaround (`docs/modules/tickets.md`'s PRD-19482 entry) was reused as-is for this round — a previously-built local clone of `node-halopsa` tag `v1.1.0` was already available at `/tmp/node-halopsa-build` from a prior session, so no new clone/build step was needed this time, only the `package.json` dependency swap for `npm install` + restore.
